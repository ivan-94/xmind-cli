XMind CLI Implementation Notes

Running notes for implementation choices, spec interpretations, intentional deviations, tradeoffs, and open questions.

2026-05-21 - Phase 0 and CLI skeleton tracer bullet

Design Decisions

  • The first TDD tracer bullet is top-level help through xmind --help. This verifies the binary name, clap wiring, command inventory, and integration test path through the public CLI.
  • The crate uses Rust edition 2021 for now. The spec allowed edition 2024 only if the initial toolchain supports it cleanly; the available local Homebrew Rust is 1.80.1, so edition 2021 is the compatible choice.
  • The initial module tree is intentionally shallow and mostly empty. Placeholder structs were avoided because clippy -D warnings would treat unused scaffold types as failures before the behavior slices need those types.
  • Dependency versions are pinned exactly for the initial slice. Cargo 1.80.1 otherwise resolves some transitive crates to newer releases that require edition 2024 manifest support.

Deviations

  • The spec describes the full CLI contract, but this slice only gives subcommands enough arguments to parse and show help. Command behavior is not implemented yet.
  • rust-toolchain.toml pins 1.80.1 to match the available local Rust, rather than using a newer stable release.

Tradeoffs

  • I chose a CLI help test before internal unit tests because it proves the crate, binary target, clap dependency, and test harness in one small public-interface slice.
  • I added a simple scripts/quality-gate.sh wrapper instead of a heavier task runner so the first gate is transparent and easy to replace later.

Open Questions

  • The machine's Homebrew Rust installation is broken: cargo and rustc fail because Rust 1.80.1 is linked against an LLVM/libunwind layout that no longer exists under /opt/homebrew/opt/llvm. I did not mutate the global Homebrew installation as part of this implementation slice.
  • Verification was completed with an official temporary Rust 1.80.1 toolchain installed under /tmp/xmind-rust.IhpKxT/toolchain. The passing gate was scripts/quality-gate.sh, which runs cargo fmt --all -- --check, cargo clippy --workspace --all-targets --all-features -- -D warnings, and cargo test --workspace --all-features.

2026-05-21 - Phase 1 help snapshots

Design Decisions

  • Help snapshots live under tests/cli/snapshots/ and are driven by a single CLI integration test target. This keeps the public command surface visible without coupling tests to internal clap types.
  • The subcommand snapshot test loops over the documented command list so adding or removing a command is a deliberate test edit.

Deviations

  • The snapshots currently capture skeleton help text with minimal argument descriptions. They should become richer as each command's real options are implemented.

Tradeoffs

  • I used snapshot tests before implementing command behavior because Phase 1 is about stabilizing the CLI shape. Behavior tests should be added command-by-command in later slices.

Open Questions

  • Command-specific option wording is still provisional until the implementation reaches each command reference.

2026-05-21 - invalid_usage JSON envelope

Design Decisions

  • Clap parse errors are handled at the binary boundary with Cli::try_parse_from. This preserves clap for normal human diagnostics while allowing --json usage errors to emit the documented agent error envelope on stdout.
  • ErrorCode includes the full documented error catalog now, with snake_case serialization and exit-code mapping, even though only invalid_usage is constructed in this slice.

Deviations

  • Command and workbook context for clap errors is inferred from argv. This is sufficient for straightforward invalid option values, but more complex parse failures may need richer clap context later.

Tradeoffs

  • I kept human invalid-usage rendering as clap's native output instead of routing all parse failures through the JSON envelope. The documented structured stream rule only applies when --json is used.

Open Questions

  • We may want to standardize whether JSON parse-error messages should preserve clap's exact text or normalize to shorter product-owned messages before the CLI contract becomes stable.

2026-05-21 - runtime file_not_found envelope

Design Decisions

  • Runtime command handling now returns an explicit process exit code from app::run. The binary boundary owns std::process::exit, while the app layer owns command context and typed runtime errors.
  • CommandEnvelope<T>, CliErrorBody, and CliWarning are shared renderer DTOs. The first runtime user is file_not_found for xmind validate <missing> --json.

Deviations

  • Runtime behavior still stops at the file-existence boundary. Existing files return success without workbook parsing until the XMind reader slice is implemented.

Tradeoffs

  • I added a human error renderer scaffold now, but kept it minimal: <command>: <message>. Rich human diagnostics, quiet behavior, and color handling remain separate Phase 2 work.

Open Questions

  • The current file_not_found error is retryable because an agent can correct the path and retry. Confirm if unreadable existing files should share this code or use a distinct future diagnostic.

2026-05-21 - minimal XMind reader and tree output

Design Decisions

  • The first reader supports modern JSON-based XMind packages by opening the workbook as a zip archive and reading content.json. The storage DTOs are private to infra::xmind::decode and convert into domain Workbook, Sheet, and Topic types.
  • tree --json --depth renders a command DTO rather than the storage DTO. At the depth boundary it emits children_count instead of nested children, matching the documented compact tree example.
  • minimal.xmind is generated from a committed minimal-content.json fixture source so the binary fixture remains explainable and reproducible.

Deviations

  • The reader currently supports only content.json, sheet id and title, root topic, child topics, topic ids, and topic titles. Notes, labels, markers, hyperlinks, images, resource metadata, unknown JSON field preservation, and unknown package entry preservation are intentionally left for later reader/writer slices.
  • Multiple-sheet selection is not implemented yet. The current tree command reads the first sheet.

Tradeoffs

  • I implemented path escaping only for the tree output path construction needed by this slice. The full TopicPath parser/renderer remains Phase 3 work and should replace this helper when path behavior is expanded.
  • SheetId is present in the domain model before it is used by selectors or output. It has a local dead-code allowance until sheet selection by id lands.

Open Questions

  • Unsupported non-content.json XMind variants currently map to parse_failed. The storage document mentions unsupported_format, but the central error catalog does not yet list that code.

2026-05-21 - sheets command

Design Decisions

  • sheets --json uses the same minimal XMind reader as tree and emits sheet id, index, title, and recursive topic count.
  • Human sheets output is a temporary concise list in workbook order: index: title.

Deviations

  • --fields and --format compact-json are not applied to sheets yet. The command currently returns the full documented sheet object for each sheet.

Tradeoffs

  • Topic count is computed from the loaded domain tree instead of storage metadata, because the current fixture reader already normalizes the full tree and this keeps the output independent of XMind internals.

Open Questions

  • Confirm whether topic_count should include the sheet root. The current implementation includes it, so the minimal fixture count is 3: Roadmap, Q2, and Payment.

2026-05-21 - patch dry-run add_tree

Design Decisions

  • The first patch slice implements xmind patch <workbook> --ops docs/examples/patch-add-tree.yaml --dry-run --json through the public CLI. It parses YAML, validates that the top-level ops array exists, resolves a path: parent selector against the first sheet, and emits planned operations plus structured added diff events.
  • Dry-run does not mutate or write the workbook. The CLI test verifies this by reading the same fixture with tree --json --depth 2 after the dry-run and confirming the original child remains unchanged.

Deviations

  • Only YAML patch files and add_tree are supported in this slice. JSON patches, aliases, multi-operation conflict handling, and apply/write behavior remain later Phase 11 and writer work.
  • The dry-run result uses a concise diff array of { event, path } entries. A richer domain DiffEvent enum and human diff renderer are still pending.

Tradeoffs

  • Parent selector resolution currently supports only simple path: selectors without full path escaping. This keeps the tracer bullet small and should be replaced by the Phase 3/4 TopicPath and selector engine.
  • serde_yaml is used for structured YAML parsing, but its indexmap/hashbrown dependency stack is pinned to versions compatible with Rust 1.80.

Open Questions

  • The example output under docs/examples/outputs/dry-run-add-tree.json reports command add-tree and an added count of 6, while the patch command contract reports command patch. This implementation follows the invoked command and counts actual new topic nodes, so the example docs may need reconciliation.

2026-05-21 - patch invalid operation diagnostics

Design Decisions

  • Patch operation DTO parsing is intentionally permissive at the YAML boundary: it reads the operation name first, then validates operation-specific fields. This lets unsupported operations return invalid_patch with operation_index and operation instead of failing as an unstructured YAML decode error.

Deviations

  • The only operation-indexed diagnostic covered so far is unsupported operation in patch --dry-run. Other patch validation failures should use the same context helpers as they are implemented.

Tradeoffs

  • The DTO keeps operation-specific fields optional, then performs validation in the patch planner. This is less strict at deserialization time but produces better agent-facing diagnostics.

Open Questions

  • Field-level schema failures still do not include field_path; that remains for the broader patch schema validation slice.

2026-05-21 - TopicPath domain type

Design Decisions

  • TopicPath now owns canonical path parsing and rendering for root paths, ordinary segments, literal slash escaping, and backslash escaping. tree output and patch parent resolution now use this domain type instead of ad hoc string concatenation and splitting.
  • Property tests cover non-empty path segment round trips. This follows the tree input contract where topic titles must not be empty and avoids the ambiguous case where a single empty segment renders the same as root.

Deviations

  • The parser currently treats any escaped character as that literal character. The documented escaping examples only require \/ and \\; stricter rejection of unnecessary escapes can be added later if the selector grammar needs it.

Tradeoffs

  • I kept the public API small: root construction, parsing selector values, rendering selector values, joining one segment, and reading segments. Parent/path editing helpers can be added when mutation slices need them.

Open Questions

  • Empty path segments are not supported as a round-trippable topic identity. This matches current title validation docs, but should be revisited if imported XMind files can contain empty topic titles.

2026-05-21 - Selector parser foundation

Design Decisions

  • The first selector slice supports root, id:, path:, and title:. Path selectors delegate to TopicPath, so escaping behavior stays centralized.
  • Patch add_tree parent validation now parses through Selector and requires a Selector::Path. This keeps diagnostics aligned with the future selector engine while preserving the current patch behavior.

Deviations

  • query: selectors are not parsed yet because the query AST and operator grammar are a larger Phase 4 slice.
  • Selector resolution still exists only as narrow patch parent path lookup. General resolution with ambiguity candidates remains pending.

Tradeoffs

  • id: and title: currently store strings directly. Stronger TopicId and title validation can be introduced when get/find start resolving selectors.

Open Questions

  • Title selector escaping/quoting is currently literal after title:. Confirm whether title selectors need quoted string parsing before user-facing find/get work.

2026-05-21 - get command and selector resolution

Design Decisions

  • get now accepts --node and optional --depth, parses selectors through the domain Selector, resolves against the first sheet, and renders result.topic using the same topic DTO shape as tree.
  • Selector miss diagnostics return not_found with the rendered selector in the error body so agents can decide to rediscover with tree or find.

Deviations

  • Selector resolution currently runs against the first sheet only. Sheet selection by title, id, and index remains pending.
  • title: resolution returns the first match instead of reporting ambiguity. Ambiguous selector candidate diagnostics are still a separate Phase 4 slice.

Tradeoffs

  • The topic output reuses TreeTopicDto to keep path/depth semantics consistent between tree and get. Detailed metadata fields such as note, labels, markers, and images will become meaningful after the reader loads them.

Open Questions

  • Confirm whether get --depth 0 should include children_count only, or also include empty metadata fields to match the command reference example.

2026-05-21 - ambiguous selector candidates

Design Decisions

  • get --node title:... now collects all title matches in sheet order. A single match resolves normally; multiple matches return ambiguous_selector with candidate id, path, title, and sheet fields.
  • A committed duplicate-title fixture source plus generated duplicate-titles.xmind covers this behavior through the public CLI instead of a domain-only test.

Deviations

  • Ambiguity detection is currently implemented for title: selectors in get. Path ambiguity from duplicate sibling titles still needs the broader selector resolution work.

Tradeoffs

  • Candidates are generated from the domain tree and current sheet title, not from storage DTOs. This keeps diagnostics independent of XMind package internals and reuses canonical TopicPath rendering.

Open Questions

  • title: still treats the selector body literally. Quoted title parsing such as title:"Payment" remains unresolved.

2026-05-21 - sheet selection

Design Decisions

  • Global sheet options now flow into command invocation state and are resolved consistently for read-style commands that need a sheet scope. The first implemented selectors are --sheet, --sheet-id, and --sheet-index.
  • tree, get, and patch now go through the same app-layer sheet resolver before operating on topics.
  • multiple-sheets.xmind is generated from a committed JSON fixture source and covers selection by index, title, and id through public tree/get CLI behavior.
  • duplicate-sheets.xmind covers duplicate sheet titles. Selecting by title now returns ambiguous_sheet with candidate sheet ids instead of silently picking the first match.

Deviations

  • Missing sheet diagnostics include the requested selector in error.details. The shared error schema allows command details, but it does not yet define a dedicated top-level sheet field.
  • Commands still default to the first sheet when no sheet selector is supplied, even for multi-sheet workbooks.

Tradeoffs

  • Sheet selection is resolved in the app layer rather than the XMind reader. This keeps package IO responsible only for loading workbook data and leaves command scope decisions with command orchestration.
  • Sheet selection also applies to patch, even though the current dry-run implementation only supports add_tree. This keeps mutation planning aligned with read command scope.
  • Sheet candidates reuse the existing candidate DTO. For sheets, the candidate id is the sheet id and path is reported as /, because the documented schema has one shared candidate list for topics and sheets.

Open Questions

  • The current precedence is index, then id, then title if multiple sheet options are supplied. The CLI does not yet reject conflicting sheet selectors.
  • Confirm whether sheet candidates should get an explicit index field instead of relying on id plus the shared topic-shaped candidate DTO.

2026-05-21 - inspect command

Design Decisions

  • inspect --json now summarizes the loaded workbook through the same reader used by sheets, tree, and get. It reports format, sheet count, per-sheet topic counts, and coarse capabilities without serializing topic trees.
  • The format value is currently reported as xmind-zen for successfully decoded modern content.json packages.

Deviations

  • capabilities.can_preserve_unknown is reported as false because the preservation bag and writer are not implemented yet. The command reference example shows the future target state where preservation is available.

Tradeoffs

  • The inspect sheet summaries reuse the existing sheet DTO, including index. The command reference example omits index, but the value is useful for recovery with --sheet-index and is already stable in sheets output.

Open Questions

  • Confirm whether inspect should keep the sheet index field or exactly match the shorter command reference example.

2026-05-21 - find title search

Design Decisions

  • find --title now performs exact, case-sensitive title matching through the public CLI and returns matches with id, path, title, sheet, and children count.
  • find --title-contains uses the same result shape and performs case-sensitive substring matching on topic titles.
  • find --contains searches case-sensitive substrings across topic title and plain-text note content. The reader now maps XMind notes.plain.content into the domain topic note field.
  • metadata.xmind is generated from a committed metadata-content.json source and covers plain note loading through public CLI search behavior.
  • find --limit truncates matches after tree-order collection. This preserves deterministic ordering while adding a simple context-control mechanism.
  • find --offset skips tree-order matches before --limit is applied. This gives deterministic offset/limit pagination over the current selected sheet scope.
  • The initial implementation searches inside the selected sheet scope and reuses the same sheet resolver as tree, get, and patch.

Deviations

  • Query-based search remains unimplemented. The documented --query behavior still needs a separate slice.
  • Supplying multiple find criteria is rejected with invalid_usage. The docs do not yet specify multi-criteria composition semantics.

Tradeoffs

  • Running find without a criterion returns invalid_usage instead of listing every topic. That keeps the first search slice aligned with the command's purpose as an explicit search tool.

Open Questions

  • Confirm whether find without an explicit sheet selector should search all sheets in workbook order, rather than following the current shared behavior of defaulting to the first sheet.
  • Confirm whether --title-contains should remain case-sensitive or gain a separate case-insensitive option later.
  • Confirm whether rich or HTML note variants should be normalized into the same note text field, or kept as separate metadata.
  • Confirm whether --limit 0 should be valid and return no matches, or rejected as invalid_usage.
  • Confirm whether --offset beyond the number of matches should silently return an empty result, as it does now, or return a diagnostic.

2026-05-21 - fields validation

Design Decisions

  • --fields is now validated for implemented read commands before workbook IO. Unknown fields return invalid_usage with field_path: "fields" and the rejected field in error.details.field.
  • Validation uses command-specific allowlists derived from docs/reference/fields.md. The current slice validates the request but does not yet trim JSON payloads.

Deviations

  • --fields on unimplemented/no-op commands is still rejected because those commands do not yet have stable payload field sets.

Tradeoffs

  • Validation lives in the app layer rather than serializers so invalid requests fail before reading the workbook and before command-specific renderers do any work.

Open Questions

  • Confirm whether tree and get should accept all topic fields during validation before those fields are loaded, or reject currently unavailable fields until metadata support is complete.

2026-05-21 - compact read output

Design Decisions

  • find --json --format compact-json --fields ... now trims each match object to the requested fields while preserving the standard command envelope and result.matches shape.
  • Without explicit --fields, compact find output keeps the documented default find fields: id, path, title, sheet, and children_count.
  • tree --json --format compact-json --fields ... now trims each topic object to requested topic fields while preserving the envelope and result.sheet/result.root structure.
  • For compact tree output, children is treated as an explicit field. If callers omit it, hierarchy is omitted even when --depth would otherwise include descendants.

Deviations

  • Compact JSON payload shaping is currently implemented for find matches and tree topics. get, sheets, and inspect still validate fields but return their existing full payloads.

Tradeoffs

  • The field trimming is done in the command renderer rather than by adding optional fields to every DTO. This keeps the first compact slice narrow and preserves existing default JSON behavior.

Open Questions

  • Confirm whether non-compact --json --fields should also trim payloads, or whether field trimming should remain tied to --format compact-json.

2026-05-22 - compact get output

Design Decisions

  • get --json --format compact-json --fields ... now trims the returned result.topic object with the same recursive topic field renderer used by tree.
  • When no fields are supplied, compact get keeps the documented default topic fields for get, excluding unloaded metadata fields from output until those fields exist in the topic DTO.

Deviations

  • Compact JSON payload shaping is now implemented for find, tree, and get. sheets and inspect still validate fields but return their existing full payloads.

Tradeoffs

  • Reusing the tree topic renderer keeps tree and get field behavior aligned, including the rule that children must be explicitly requested in compact output.

Open Questions

  • Confirm whether compact get should emit explicit empty metadata fields such as labels or omit unavailable fields until those fields are implemented.

2026-05-22 - compact sheets output

Design Decisions

  • sheets --json --format compact-json --fields ... now trims each sheet object while preserving the standard command envelope and result.sheets array shape.
  • root_topic_id is now included in the internal sheet DTO because it is a documented legal sheet field and cannot be projected without loading it from the root topic.

Deviations

  • Full non-compact sheets --json may now include root_topic_id as an additional sheet field. The compatibility policy allows additive JSON fields, and exposing it keeps full output aligned with the documented field vocabulary.
  • Compact JSON payload shaping is now implemented for find, tree, get, and sheets. inspect still validates fields but returns its existing full payload.

Tradeoffs

  • Sheet field projection is implemented in the app renderer, matching the existing compact read-command approach, instead of introducing a generic projection framework before more commands require it.

Open Questions

  • Confirm whether root_topic_id should remain visible in full sheets --json output or only appear when explicitly requested through compact fields.

2026-05-22 - compact inspect output

Design Decisions

  • inspect --json --format compact-json --fields ... now trims workbook-level fields while preserving the envelope and returning a compact result object.
  • The inspect result now carries file and resources_count so all documented workbook fields can be validated and projected.

Deviations

  • resources_count currently reports 0 because the resource index and asset loading slices are not implemented yet. This keeps the field available for agents without claiming resource parsing support.
  • Compact JSON payload shaping is now implemented for all listed Phase 6 read-command payloads: find, tree, get, sheets, and inspect.

Tradeoffs

  • Inspect field projection is limited to top-level workbook fields. Nested sheets summaries are emitted as sheet DTOs rather than introducing nested field selection syntax not described by the spec.

Open Questions

  • Confirm whether resources_count should remain 0 until resources are loaded, or be omitted/null when the resource index is unavailable.

2026-05-22 - validate command baseline

Design Decisions

  • validate --json now performs a real workbook read and returns the documented validation result shape: valid, warnings, and errors.
  • The baseline validator treats successful package decoding as a valid workbook for this slice. Parse and file errors still use the shared structured error path.

Deviations

  • Deep structural checks such as cycle detection, id policy, ordering, unknown-field preservation, and strict warning handling are not implemented yet. The command reports no validation warnings or errors until those validation passes exist.
  • The documented --strict option is accepted by the parser in a later 2026-05-22 slice, but warning-to-failure semantics still need a later validation pass once warnings are meaningful.

Tradeoffs

  • This keeps validate useful as an agent-safe readability check now without inventing shallow structural failures that would be hard to justify from the current domain model.

Open Questions

  • Confirm whether validate should eventually emit detailed validation diagnostics inside result.errors or fail with validation_failed as soon as any validation error is found.

2026-05-22 - validate strict option

Design Decisions

  • validate --strict is now accepted by the CLI parser and routed through the validate action.
  • With the current baseline validator, strict mode produces the same successful result as non-strict mode when there are no warnings or validation errors.

Deviations

  • Strict mode does not yet convert warnings into failures because the implementation does not have warning-producing validation passes yet.

Tradeoffs

  • The option is wired now to keep the command reference and parser compatible while avoiding speculative warning semantics.

Open Questions

  • Confirm whether strict warning failures should return validation_failed with exit code 9, or keep ok: true with result.valid: false.

2026-05-22 - topic label loading

Design Decisions

  • Modern XMind topic labels are read from the topic-level labels string array in content.json. Missing labels default to an empty array in the domain model and JSON output.
  • The metadata fixture now includes labels on the existing Payment topic so the public get --json path verifies package decode, domain conversion, and output rendering together.

Deviations

  • This slice only loads and renders labels. Query predicates, mutation commands, and package write-back semantics for labels remain separate PLAN items.

Tradeoffs

  • I used the direct labels: string[] representation already documented for topic-tree schemas instead of adding a storage-specific wrapper type before another observed XMind variant requires it.

Open Questions

  • Confirm whether labels should later participate in find --contains and query expressions before marker and hyperlink support are implemented.

2026-05-22 - topic marker loading

Design Decisions

  • Modern XMind topic markers are read from topic-level markers objects with a markerId field. The CLI domain and JSON output expose those marker ids as a simple string array.
  • The metadata fixture uses two marker ids on the existing Payment topic so the public get --json path verifies package decode and renderer behavior together.

Deviations

  • This slice only loads and renders marker ids. Marker query predicates, semantic marker aliases, and marker mutation remain separate PLAN items.

Tradeoffs

  • I kept marker values as raw ids such as priority-1 rather than translating them to display names. Raw ids are stable for agents and match the existing command references.

Open Questions

  • Confirm whether future marker search should match only raw marker ids or also product-owned aliases for common priority/task markers.

2026-05-22 - topic hyperlink loading

Design Decisions

  • Modern XMind topic hyperlinks are read from the topic-level href field in content.json. The CLI domain and JSON output expose this value as hyperlink to match the documented semantic model.
  • Missing hyperlinks remain absent from full JSON topic output and are omitted from compact field rendering unless a topic actually has a hyperlink value.

Deviations

  • This slice only loads and renders hyperlink values. Hyperlink query predicates and mutation semantics remain separate PLAN items.

Tradeoffs

  • I kept the domain field named hyperlink while mapping from storage href, so callers do not need to know the package field name.

Open Questions

  • Confirm whether future validation should reject non-URL hyperlink targets or preserve supported XMind-internal link targets as opaque strings.

2026-05-22 - topic image reference loading

Design Decisions

  • Topic image references are read when modern XMind topic JSON exposes an image object with a src value. The first semantic output maps that value to image.asset_id and carries optional alt and title strings.
  • Image references are omitted from JSON output when absent. This keeps existing read snapshots stable while allowing --fields image to expose the reference for topics that have one.

Deviations

  • This slice does not inspect package resource entries, infer media types, compute byte sizes, or validate that the referenced asset exists. Those behaviors belong to resource metadata and asset fixture PLAN items.

Tradeoffs

  • I kept the initial asset_id equal to XMind's src reference because no resource index exists yet to assign product-owned asset ids without inventing a second mapping.

Open Questions

  • Confirm whether future resource indexing should preserve xap: references as asset ids or map them to generated ids while retaining package paths as internal metadata.

2026-05-22 - no-color human errors

Design Decisions

  • Runtime human error output now colors the command prefix red by default and preserves a plain command prefix when --no-color is provided.
  • JSON error envelopes remain uncolored and continue to write structured errors to stdout.

Deviations

  • Clap parse errors still use clap's own renderer. This slice covers application runtime errors because those are rendered by the product error pipeline.

Tradeoffs

  • I limited color to the command prefix rather than coloring the full message, so copied diagnostics remain readable and stable.

Open Questions

  • Confirm whether command help and clap parse errors should also be normalized through the product renderer before the CLI contract is considered final.

2026-05-22 - exit code mapping coverage

Design Decisions

  • The complete documented ErrorCode to process exit-code mapping is covered by a focused Rust test on ErrorCode::exit_code.

Deviations

  • Not every error code has a dedicated end-to-end CLI scenario yet. This slice covers the mapping table itself; command-specific error behavior remains tracked by later PLAN items.

Tradeoffs

  • A mapping-table test is less brittle than forcing artificial CLI scenarios for errors whose commands are not implemented yet.

Open Questions

  • None for the mapping table. Future command tests should still verify representative runtime paths use the mapped exit code.

2026-05-22 - AssetId domain type

Design Decisions

  • AssetId is a small domain wrapper with explicit new and as_str methods. Storage decoding and JSON DTO rendering now use this interface instead of directly reading the tuple field.

Deviations

  • The type does not yet validate id format. At this stage asset ids can still be XMind source references such as xap:resources/... until resource indexing establishes a product-owned id scheme.

Tradeoffs

  • A minimal wrapper keeps current image-reference support simple while giving later resource metadata work one place to add validation or normalization.

Open Questions

  • Asset id normalization remains tied to the future resource index design.

2026-05-22 - TopicImageRef domain type

Design Decisions

  • TopicImageRef now has an explicit constructor that groups the asset id with optional accessible text fields alt and title.
  • XMind storage decoding constructs image references through this domain constructor instead of assembling the struct inline.

Deviations

  • The type remains reference-only. It does not yet carry media type, byte size, checksum, or package-entry metadata because those belong to the resource metadata/indexing PLAN items.

Tradeoffs

  • Keeping image reference metadata small avoids coupling topic reads to resource scanning before the resource index contract is implemented.

Open Questions

  • Confirm whether title should remain separate from alt in all import/export formats or collapse to one display label in human renderers.

2026-05-22 - ResourceIndex scaffold

Design Decisions

  • Workbook now owns a ResourceIndex, and inspect reads resources_count from that index instead of using a hard-coded zero.
  • The reader initializes an empty resource index until package resource scanning is implemented.

Deviations

  • This is only the domain container. It does not yet load package entries, media types, sizes, checksums, or usage data.

Tradeoffs

  • I avoided exposing an unfinished Asset API in production code. The only runtime method needed now is len(); test helpers stay behind cfg(test).

Open Questions

  • Resource metadata loading still needs to define the full asset DTO and id normalization rules.

2026-05-22 - PreservationBag scaffold

Design Decisions

  • Workbook now owns a PreservationBag that can hold raw JSON fields and package entry names once preservation readers are implemented.
  • The XMind reader initializes an empty preservation bag. Inspect capabilities report unknown preservation as unavailable until the bag contains preserved data.

Deviations

  • This is only the domain container. It does not yet capture unknown package entries or unknown JSON fields from actual workbooks.

Tradeoffs

  • The production API exposes only is_empty() for now. Mutation and writer code can expand the bag API when it starts merging preserved data.

Open Questions

  • Confirm whether topic-level preservation should live in each Topic or stay in a workbook-level indexed bag once unknown JSON field preservation is implemented.

2026-05-22 - query evaluator field coverage

Design Decisions

  • Query evaluator tests now cover every documented query field: id, title, note, path, label, marker, hyperlink, image, depth, and children_count.
  • label and marker are evaluated as string collections. hyperlink is an optional string, and image currently supports exists.

Deviations

  • The documented fields are singular label and marker, matching query documentation rather than the output DTO field names labels and markers.

Tradeoffs

  • Collection inequality means the queried value is absent from the collection. This is useful for audits like label != "Deprecated".

Open Questions

  • Confirm whether aliases labels and markers should also be accepted in query expressions for symmetry with output field names.

Deviations

  • The preservation bag currently records entry names only. Reusing the preserved bytes during writes remains a later writer PLAN item.

Tradeoffs

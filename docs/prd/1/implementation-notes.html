Parent Agent Plan

  • 父集成分支： codex/prd-1-github-release-e2e-program。
  • Slice 分支模式： codex/slice-1-<issue>-<slug>。
  • Slice worktree 模式： .scratch/worktrees/prd-1/<issue>-<slug>。
  • 子 Agent 恢复模式为 resumable：父 Agent 记录 agent id，返工时优先 用同一逻辑 worker 在同一 worktree/branch 追加修复 commit。
  • 每个 Slice 必须执行 TDD 或等价红绿重构实践，并在自己的分支提交； 子 Agent 不 push、不创建 PR、不运行 cross-review、不准备 HAT。

Current Decisions

  • 远端仓库初始没有任何 branch；父 Agent 已将当前绿色基线 master 推送为 PR base。
  • #3 branch protection 和 #11 real XMind golden fixture generation 带有人类/权限依赖。自动化部分可以交付，无法由 Agent 独立验证的权限或 GUI 步骤必须记录为 remaining risk。
  • Phase 17 命令行为闭环优先保持文档契约；若 diff 的输入形态与文档目标冲突，Slice Agent 必须停止并回报父 Agent，而不是 擅自收窄行为。
  • Slice #4 CI merge gate uses a named Stable PR E2E subset placeholder job rather than running E2E commands immediately, because the stable PR E2E harness is tracked separately by issue #12. The placeholder is intentionally dependency-ordered after the Rust quality gate so branch protection can later require the same check name when the real harness replaces it.

Slice #10 Fixture Manifest Decision

  • 当前已提交的有效 tests/fixtures/xmind/*.xmind 文件由仓库内 JSON fixture 内容生成，并非 XMind App 保存的 golden fixture；因此 tests/fixtures/xmind/manifest.md 将它们标记为 synthetic-generated。
  • real-xmind-app 保留给后续 #11 从真实 XMind App 生成或保存的代表性用户 fixture。本 Slice 不伪造真实 App 来源，也不新增 golden fixture。
  • malformed.xmind 是故意损坏的错误路径 fixture，标记为 synthetic-corrupt，避免后续 Agent 将其当成代表性用户文件。

Open Risks

  • PRD 范围很大，多个 Slice 会触碰 CLI 行为、E2E 测试、发布配置和文档； 父 Agent 合并时必须优先保留各 Slice 的边界并运行集成验证。
  • #3 需要 GitHub branch protection 权限，可能只能交付脚本、 文档和验证命令，最终启用由 maintainer 完成。
  • #11 可能需要本机 XMind App/GUI 介入；若无法无损自动生成真实 fixture，应提交 manifest/governance 和明确 TODO，而不是伪造为真实 App 产物。

Slice #11: Real XMind Fixture Handoff

  • 2026-05-23 本机发现 /Applications/Xmind.app， CFBundleIdentifier 为 net.xmind.vana.app， CFBundleShortVersionString 为 26.02.04171， 且 codesign --verify --deep --strict 通过。
  • XMind 没有可用的 AppleScript scripting definition： sdef /Applications/Xmind.app 返回 error -192，因此自动保存只能走 GUI。
  • GUI 探索中，XMind 拒绝打开由 tests/fixtures/xmind/minimal.xmind 复制出来的文件，提示 “无法打开文件/文件可能已损坏”；不能通过重存 synthetic fixture 伪装成 real app fixture。
  • 新建 workbook 的 Command+Shift+S 流程能到达“当前设备” macOS Save panel，但本次 Computer Use 路径选择未能在 worktree 中实际创建 文件。因此本 slice 未新增任何 real-xmind-app fixture。
  • 后续人工步骤、每个 fixture 必跑的 xmind inspect / xmind tree / xmind validate 命令，以及 remaining acceptance gaps 已记录在 tests/fixtures/xmind/manifest.md 的 Issue #11 Real XMind App Handoff 小节。

Slice #7: Release Policy Documentation

  • 决策：issue #7 的 release policy 入口先落在 docs/README.md 与 docs/technical/README.md； 父集成分支合入 #2 后，根 README.md 也会作为发布与安装状态的 用户入口继续由后续安装、release 和 Homebrew slices 更新。
  • 决策：docs/technical/release-policy.md 只定义版本、changelog、 GitHub Release notes 和 SHA256SUMS 规则，不初始化 cargo-dist、安装脚本、Homebrew tap 或平台矩阵。
  • 风险：最终 artifact 文件名仍依赖 #5/#6/#8/#9；本 slice 使用 SHA256SUMS 作为稳定校验清单名称，后续发布自动化需要与之保持一致。

Slice #5: cargo-dist Release Workflow

  • 决策：本 slice 在 Cargo.toml 中加入最小 [workspace.metadata.dist] 配置，并新增 .github/workflows/release.yml，从 v* tag 触发 GitHub Release artifact 构建。
  • 决策：为避免越界到 #6 平台矩阵，本 slice 只配置 x86_64-unknown-linux-gnu 作为 cargo-dist 最小目标。
  • 偏差：cargo-dist 0.31.0 本地安装在仓库 pinned Cargo 1.80.1 下失败， 因 transitive crate manifest 需要 edition2024。本 slice 已用契约测试覆盖 checked-in release 配置，真实 cargo dist plan 仍需在可运行 cargo-dist 的工具链或预装二进制环境中复验。

Slice #6: Release Platform Matrix And Binary Smoke

  • 决策：首个 GitHub Release 二进制矩阵明确为 aarch64-apple-darwin（macOS Apple Silicon）、 x86_64-apple-darwin（macOS Intel）、 x86_64-unknown-linux-gnu（Linux x86_64 GNU）和 x86_64-pc-windows-msvc（Windows x86_64 MSVC）。
  • 决策：release workflow 在每个 native runner 上执行 dist build --target=${{ matrix.target }} --artifacts=local 后，只运行薄冒烟检查： xmind --version、 xmind tree tests/fixtures/xmind/minimal.xmind --json 和 xmind validate tests/fixtures/xmind/minimal.xmind --json。 完整命令矩阵仍归 Rust E2E PR/full matrix 测试，不在 release artifact job 中重复。
  • 偏差/风险：macOS runner 选择按 GitHub-hosted runner 当前能力使用 macos-14 覆盖 Apple Silicon、macos-15-intel 覆盖 Intel；若 GitHub 之后调整 runner 标签或弃用镜像，release workflow 需要同步更新。
  • 非目标：本 slice 不实现 install script、Homebrew、crates.io、容器镜像、 Linux arm64、Linux musl/static、macOS universal binary、Windows GNU 或 32-bit Windows 支持；README/install/release policy 已避免暗示这些平台可下载。

Slice #12: Rust E2E Harness

  • 决策：默认 PR E2E 子集落在独立测试目标 e2e_pr_subset，完整矩阵入口落在可单独过滤的 e2e_full_matrix；CI 中保留同一个检查名 Stable PR E2E subset，但从占位说明改为执行 cargo test --test e2e_pr_subset --all-features。
  • 决策：可写命令的默认 PR 子集只操作临时目录中的 fixture 副本，并在 apply 后运行 validate --json；测试同时比对源 fixture 字节， 用于证明 committed fixture 没有被写路径污染。
  • 偏差：当前 diff --json 会以 0 退出但不输出 JSON envelope。 Slice #12 只把它作为成功路径纳入默认子集，不在本 slice 中修复 diff 合约；该行为仍归后续 #20 收敛。
  • 偏差：当前 patch --apply 明确返回 invalid_usage，因为事务写入由后续 #19 负责。 默认 PR 子集覆盖 patch --dry-run 成功路径和 patch --apply 的稳定错误路径，而不是提前实现 apply。

Slice #13: Read Command E2E Coverage

  • 决策：issue #13 的用户视角 read/validate 覆盖落在 tests/e2e/pr_subset_test.rs，复用 issue #12 建立的 Rust E2E harness。覆盖范围包括 inspect, sheets, tree, get, find 和 validate 的 JSON 成功路径、关键 human 输出、代表性错误、字段裁剪、sheet/topic 选择、assets、分页和 invalid usage。
  • 决策：本 slice 只补 E2E 覆盖与测试支持，不改变 CLI 行为。新增的 run_human_error 与 unsupported workbook fixture writer 仅用于从 用户接口验证现有错误输出和 unsupported format 分支。
  • 偏差：validate 的 warnings、--strict warning failure 和 structural validation failure 仍依赖后续 issue #21 的真实 validation 实现。本 slice 在 E2E 中保留 #[ignore] pending tests 作为覆盖占位，而不是提前制造 warning fixture 或修改 validate 行为。
  • 验证：2026-05-23 运行 PATH=/opt/homebrew/opt/rustup/bin:$PATH cargo test --test e2e_pr_subset read_e2e_ 通过，结果为 7 passed、2 ignored；随后运行 PATH=/opt/homebrew/opt/rustup/bin:$PATH cargo test --test e2e_pr_subset 通过，结果为 12 passed、2 ignored；最后运行 PATH=/opt/homebrew/opt/rustup/bin:$PATH cargo test --workspace --all-features 通过；PATH=/opt/homebrew/opt/rustup/bin:$PATH ./scripts/quality-gate.sh 通过。
